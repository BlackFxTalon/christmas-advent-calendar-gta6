# Архив улик на Node.js: как встроить в текущий бот

**Статус:** подключено к рабочему боту и проверено 37 unit/интеграционными тестами.

## Главное решение: Telegraf не нужен

В проекте нет Telegraf. Бот построен на `node:http` и `pg`, а логика разделена на два слоя:

1. **`engine.mjs`** — чистая функция `handleUpdate(update) → actions[]`. Она не делает сетевых вызовов, а только описывает, что отправить: `message`, `photo`, `callbackAck`.
2. **`server.mjs`** — принимает webhook и проверяет секрет. Внутри `processUpdate` открывает транзакцию с дедупликацией по `update_id`, затем исполняет actions через Telegram Bot API.

На этом разделении держатся три вещи, которые уже работают: повтор webhook не дублирует прогресс, сбой обработки откатывает транзакцию, а логику можно тестировать без сети. Если подключить Telegraf, он стал бы вторым маршрутизатором апдейтов. Тогда пришлось бы либо отказаться от `processUpdate`, либо оборачивать в него каждый обработчик Telegraf. Поэтому архив сделан так же, как движок: **update на вход, actions на выход**.

Если в будущем всё же понадобится Telegraf, функции прототипа переносятся почти без изменений. Ниже показано соответствие; это не рекомендация.

```js
// Только для сравнения. С Telegraf пропадают processUpdate-транзакция и replay receipts.
bot.command("archive", async (ctx) => run(ctx, await handleArchiveCommand(ctx.message, deps)));
bot.action(/^ar:/, async (ctx) => run(ctx, await handleArchiveCallback(ctx.callbackQuery, deps)));
```

## Модель состояний

Состояние дела **не хранится отдельно**: оно вычисляется из `bot_case_progress`, который движок уже ведёт.

| Состояние | Условие | Что видит игрок |
|---|---|---|
| `locked` | строки прогресса нет | дело не показывается в архиве |
| `open` | `status = 'in_progress'` | дело и его материалы |
| `solved` | `status = 'completed'` | дело, материалы и строка «Итог» |

Улика проходит путь `unseen → viewed`. Это единственное новое состояние, и для него нужна таблица `bot_evidence_views`. Без неё архив тоже работает, только без метки «новое».

Два правила вытекают из этой модели:

- **Архив только повторно открывает уже выданное.** Кнопки архива не меняют статус дела: «решено» ставит только движок после правильного ответа.
- **`callback_data` не подтверждает доступ.** Его формирует клиент, поэтому при каждом нажатии доступ перепроверяется по прогрессу из БД. Тест «подделанный callback к закрытому делу» проверяет именно это.

## Формат callback_data

Telegram ограничивает `callback_data` 64 байтами. Используется короткая схема, где фильтр и страница переходят в каждую кнопку, поэтому «Назад» возвращает ровно туда, откуда игрок пришёл:

```text
ar:l:<view>:<page>                         список дел
ar:c:<caseId>:<view>:<page>                карточка дела
ar:e:<caseId>:<evidenceId>:<view>:<page>   улика
```

Самая длинная строка, например `ar:e:12:h3-frame:solved:9`, занимает 25 байт.

## Что подключено к рабочему боту

1. **Данные дел.** Все 12 дел в `cases.mjs` содержат структурированные материалы, derived evidence, summaries и карточки PNG.
2. **Движок.** `engine.mjs` маршрутизирует `/archive` и callback-и `ar:`; архив доступен только в личном чате.
3. **Сервер.** `dispatch()` поддерживает:
   - новый тип `editMessage` → `editMessageText` с `chat_id`, `message_id`, `text` и `reply_markup`. Ошибку `400 message is not modified` нужно считать успехом: игрок мог дважды нажать ту же кнопку;
   - в `sendPhoto()` передавать `reply_markup` (как JSON-строку в `FormData`), иначе под фото улики не появится кнопка «← К делу». Также поле `text` у `callbackAck` нужно передавать в `answerCallbackQuery`, чтобы игрок видел всплывающее «Это дело ещё не открыто».
4. **Хранилище.** `progress-store.mjs` предоставляет `markViewed` и `getViewed` с graceful fallback при отсутствии таблицы; миграция `005_evidence_views.sql` применяется вручную.
5. **Тесты.** `archive.test.mjs` находится в `bot/test/`; HTTP-интеграционный тест проверяет сценарий «/archive → дело → улика» с подменёнными Telegram API и PostgreSQL.

## Ограничения, о которых стоит помнить

- **Replay receipts.** При повторной доставке webhook `processUpdate` повторяет сохранённые actions. Для `editMessage` это безопасно, потому что результат тот же; повторное фото улики игрок получит второй раз, но только если первая отправка не была отмечена доставленной.
- **Подпись к фото ограничена 1024 символами.** Если текст улики длиннее, прототип отправляет фото с заголовком и следом отдельное сообщение с текстом.
- **Подсказки в архиве не показываются.** Они остаются кнопками под сообщением дела, чтобы архив не превратился в способ подсмотреть решение.
