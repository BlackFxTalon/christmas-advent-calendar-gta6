# Telegram-бот «12 дней до полуночи» — прототип

В папке находятся ядро диалога, webhook-адаптер, PostgreSQL-хранилище прогресса и архив улик. Подключены все 12 дел календаря; тексты и ответы совпадают с текущим сценарием в `content/cases-01-12.md`. PostgreSQL-схема совместима с Supabase; код не требует включения managed database в WebDev.

## Логика и сохраняемые данные

- `/start`, `/help`, `/today`, `/progress`, `/archive`;
- `/case N` для всех 12 дел только при `BOT_PREVIEW_MODE=1`;
- выдача дел по датам 20–31 декабря с настраиваемым `BOT_TIME_ZONE`;
- подсказки в три ступени через inline-кнопки или `/hint 1`;
- проверка ответов, включая разрешённые варианты; неверный ответ не блокирует следующую попытку;
- отправка карточки улики отдельным фото-сообщением;
- архив улик с inline-кнопками, фильтрами, пагинацией и отметкой просмотренных материалов;
- состояние сохраняется отдельно по Telegram `from.id` и номеру дела: начато/решено, число попыток, достигнутая ступень подсказки, времена начала и решения.
- webhook дедуплицирует входящие `update_id` через `bot_update_receipts`; receipt и изменения прогресса фиксируются в одной PostgreSQL-транзакции.
- если Telegram повторит update до подтверждения доставки, бот повторно отправит сохранённые исходящие actions, не выполняя игровую логику повторно. При сетевом сбое после фактической отправки Telegram возможен повтор самого сообщения: БД и Telegram API не поддерживают общую транзакцию.
- одноразовые callback-ack IDs не сохраняются; payload actions очищается после успешной доставки, а `update_id` остаётся как ключ дедупликации.

Бот не записывает имя пользователя, входящий текст переписки или введённые ответы. В `bot_update_receipts` сохраняется ID обновления и только ожидающие отправки actions; после успешной отправки actions удаляются и устанавливается `delivered_at`. Команда `/progress` показывает сводку только в личном чате. Хранилище работает через PostgreSQL-драйвер `pg`; Supabase подключается через серверный `DATABASE_URL`.

## Локальная проверка без секретов и базы

```bash
cd bot
pnpm install
pnpm test
```

37 тестов используют тестовое хранилище, mock PostgreSQL pool и HTTP-интеграционный mock Telegram: `node --test` проверяет логику, webhook, архив и транзакционный контракт, но сам по себе не проверяет сетевое подключение к Supabase.

## Интерактивный симулятор без базы и Telegram

```bash
pnpm simulate
```

Для сквозной проверки календаря и всех 12 дел используйте `node scripts/simulate-all.mjs`.

Симулятор передаёт введённые сообщения в тот же `engine.mjs`, что и бот, но сохраняет прогресс только в памяти процесса. Используйте `/start`, `/today`, `/archive`, `/hint N 1`, `/progress` и вводите ответы обычным текстом. После `/case N` симулятор автоматически связывает следующий текстовый ввод с выданной загадкой. Для нажатия последней показанной inline-кнопки введите `:button` (или `:button 2` для второй кнопки); `:buttons` выводит список. Чтобы проверить календарь, задайте дату командой, например `:date 2026-12-20T12:00:00Z`, и введите `/today`. `:reset` сбрасывает прогресс, `:quit` завершает симулятор. Изображения улик не отправляются — показывается только путь к файлу. Ни `DATABASE_URL`, ни токен Telegram не нужны. PNG-карточки всех дел лежат в `public/evidence/`; при необходимости их можно пересоздать скриптом `scripts/generate-evidence-cards.ps1` через Windows PowerShell.

## Подготовка схемы — только при отдельном подключении

Миграция `migrations/001_player_progress.sql` создаёт таблицы профилей и состояния дел. После того как владелец настроит `DATABASE_URL` как серверный secret, базовую миграцию можно применить отдельной командой:

```bash
pnpm run migrate
```

Команда `pnpm run migrate` сейчас применяет только `001_player_progress.sql`; миграция `005_evidence_views.sql` не применяется автоматически и должна быть применена вручную после базовых миграций. Миграция `migrations/004_update_idempotency_and_advisor_hardening.sql` уже применена к текущему Supabase-проекту; при настройке отдельной БД применяйте её через административную роль после `001` и `003`. Она создаёт receipts, закрепляет `search_path` и сохраняет закрытый API-доступ к трём старым таблицам. Не запускайте её под `bot_app`.

## Серверные переменные

- `TELEGRAM_BOT_TOKEN` — токен от BotFather;
- `TELEGRAM_WEBHOOK_SECRET` — секрет webhook из букв, цифр, `_` и `-` (1–256 символов);
- `DATABASE_URL` — PostgreSQL URL из Supabase или другого PostgreSQL-хоста;
- `BOT_TIME_ZONE` — часовой пояс календаря, по умолчанию `Europe/Moscow`;
- `BOT_PREVIEW_MODE=1` — ручная выдача `/case N` только для закрытого теста; не включать в публичном боте.

Реальные значения нельзя помещать в репозиторий или клиентский код; образец находится в `.env.example`. Сервер с включённым хранилищем без `DATABASE_URL` не запускается.

## Отдельная роль PostgreSQL и локальные секреты

После `002_bot_rls.sql` миграция `003_bot_app_role.sql` создаёт роль `bot_app` без LOGIN, без `BYPASSRLS`, без DDL и без права удаления. Ей выдаются только SELECT/INSERT/UPDATE и соответствующие разрешающие RLS-политики. Этот доверенный серверный бот имеет доступ ко всем строкам прогресса; не используйте эти credentials в браузере. Миграция не содержит пароль и не применялась автоматически.

Сначала примените `003_bot_app_role.sql` под административной ролью в Supabase SQL Editor. Чтобы задать пароль без записи открытого значения в SQL-историю, подключитесь `psql` к базе как администратор и выполните `\password bot_app`; затем выполните `ALTER ROLE bot_app WITH LOGIN;`. Пароль вводится в скрытом интерактивном запросе. Если прямое подключение с Windows недоступно, скопируйте параметры **Session pooler** из **Connect** в Supabase Dashboard; не придумывайте pooler-хост вручную.

Для проверки после создания роли запустите `scripts/test-rls-roles.sql` под администратором в SQL Editor. Скрипт временно выдаёт `anon` и `authenticated` права только внутри транзакции, проверяет, что политики блокируют чтение и запись, затем проверяет SELECT/INSERT/UPDATE для `bot_app` и отсутствие DELETE. В конце выполняется `ROLLBACK`, поэтому фикстуры и временные гранты не сохраняются. Если SQL-клиент остановится на ошибке до последней строки, выполните `ROLLBACK` в этой сессии.

Для локальной разработки скопируйте `.env.example` в `.env` и заполните значения только на своём компьютере. `.gitignore` исключает `.env` из Git. Для запуска с переменными из файла используйте `pnpm start:local` (Node.js 20.6+); обычный `pnpm start` ожидает, что секреты уже переданы окружением процесса. В production задавайте их через секрет-хранилище хостинга, не загружая `.env` в репозиторий или frontend. Используйте `DATABASE_URL` с пользователем `bot_app`, а URI/host/port берите из Supabase **Connect**. Для direct connection имя пользователя — `bot_app`; для shared pooler — `bot_app.<project-ref>`. Пароль должен быть URL-encoded, если содержит спецсимволы. Проверьте сетевой режим и SSL-параметры по строке Connect; не отключайте TLS-проверку.
